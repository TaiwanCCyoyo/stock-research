# Git Workflow Contract

Shared by Codex and Claude Code. Use native Git and GitHub capabilities; commit skills own local verification and commits.

## Task isolation

- Never commit or push to the default branch. Every change reaches it through a pull request. This rule is absolute; the rest of this section is guidance.
- Work on a branch other than the default. A dedicated task branch is preferred when the change will become its own pull request, but a long-lived general branch such as `workspace/<agent>` is fine for ongoing, exploratory, or multi-step work. Read-only work needs no new branch, and explicit user checkout instructions take precedence.
- Before writing changes for a new request, fetch `origin` and build on the latest default branch, so work does not duplicate or conflict with changes merged elsewhere. An independent request starts a new task branch, in a new worktree when the current one holds other work, from the fetched default branch; do not add it to a branch whose commits belong to another open or squash-merged PR. Follow-up work on the same task updates that task's branch instead: rebase onto the default branch while its commits are unpushed, and merge the default branch in once they are pushed, because rebasing pushed commits requires a force push. Report when the default branch cannot be refreshed.
- Use a separate worktree when isolation helps. Place worktrees under `<primary-checkout>/.worktrees/<name>/`, not `.tmp/`, and resolve this path from the primary checkout even when operating inside a linked worktree. Reserve `.tmp/` for temporary reports, probes, and disposable artifacts.
- Keep one primary writer per worktree. Before reusing an existing worktree, check its ownership and uncommitted changes.
- Preserve unrelated work. Subagents operate within the parent-assigned scope; they do not independently publish or integrate changes.

## Worktree lifecycle

Worktrees belong to the session that created them, with ownership recorded in its task report or handoff. An inventory provides evidence, not ownership or deletion authorization. Apply this section before creating a worktree and before reporting completion; do not rely on an optional session hook to enforce it.

1. **Reuse one checkout per task branch.** Follow-up work reuses its existing worktree after checking ownership and changes. Prefer `git show`, `git diff`, or `git archive` for read-only inspection of another commit. Do not create another worktree for a branch that already has one.
2. **Inventory before creating.** Run `uv run python scripts/worktree_inventory.py --repo <checkout>` from a checkout containing the tool. It reports paths, branch or detached HEAD, commit and date, PR state and head/base evidence, tracked changes, untracked files, and ignored file bytes. Registered nested worktrees are excluded from their parent's byte scan and measured separately. GitHub lookup uses authenticated `gh`; `--no-pr` supports offline or other-host use, and `--json` provides a reusable report. For another host, verify its PR/MR state separately. Unavailable or ambiguous evidence is unknown, never proof of no PR or a safe cleanup candidate. PR state, not task-commit ancestry, establishes a merge; squash merges need not contain the task commits. A mismatch between the current HEAD and the PR final head blocks cleanup based on that PR.
3. **Remove session-owned probes before reporting.** A detached checkout used only to inspect, reproduce, or verify a commit lasts only for that session. Record findings first, check preservation and ownership, then remove it using normal Git or the host's lifecycle tool. This contract authorizes removal only of probes created by the acting session; never force removal. A detached inventory entry alone does not prove a disposable probe. If a probe must survive for a reviewer, name it `probe-<task>-<sha>` and record its path, owner, purpose, and removal condition in the handoff. Clean your own merged task worktrees under [Post-merge cleanup](#post-merge-cleanup) before adding another, when that project has authorized it; otherwise report the required owner decision.
4. **Keep a budget of five worktrees per session.** The primary checkout does not count. Before exceeding five, clean eligible session-owned resources or tell the owner why each retained checkout is still needed. Other sessions' worktrees are not yours to clean or count as your holdings.
5. **Report potentially abandoned work.** If a worktree has no PR and its latest commit is at least seven days old, summarize its contents and known ownership to the owner. Commit age alone does not establish inactivity: consider uncommitted work and session activity. Do not delete it without the owner's decision.
6. **Preserve before removal.** Inspect tracked changes, untracked files, and needed ignored data; clean status does not prove ignored data is disposable. Inventory byte totals are not a preservation audit and omit ignored files inside tracked submodules; Stock additionally follows [Data And Worktrees](stock-agent-operations.md#data-and-worktrees). Check processes, initialized submodules, and linked directories before removal; do not follow links into shared data or force removal of initialized submodules. Move only your needed artifacts to their canonical home within authorized scope, or report the preservation blocker and retain the checkout. Never delete shared or unowned resources. In the completion report list each session-owned checkout as open PR, merged and removed, or retained with a reason; explicitly report when no worktree was created.

## Review and integration

- A review request authorizes analysis and a report. Publishing review comments or a formal approval requires explicit authorization or an owner-enabled reviewer role scoped to the repository. Review authority does not include merge authority.
- Review the PR's current head commit and identify it in the result. New commits require renewed review; an internal reviewer report is not a GitHub approval.
- Agent sessions must not directly push the default branch, bypass quality gates, or change repository rules. Merging is the owner's decision and must go through a PR whose required checks pass.
- Force pushes, history rewrites, discarding work, and deleting branches/worktrees require explicit authorization. [Worktree lifecycle](#worktree-lifecycle) authorizes only the acting session's preserved inspection probes; [Post-merge cleanup](#post-merge-cleanup) covers only the specified merged-task cleanup. Before authorized cleanup, verify the task result is preserved and no other session owns the worktree.

## PR follow-through

For an authorized implementation PR, the main agent owns the following work without waiting for another user reminder. A review-only or status-only request remains read-only unless the user also authorizes implementation.

1. After opening the PR, wait for initial CI and the configured review. For initial and renewed review, prefer a tool that waits for status changes when available; otherwise sleep between status queries, starting at three minutes and backing off to five minutes while review is still running. These are polling intervals, not completion deadlines. Keep waits interruptible and within host limits; report meaningful changes rather than unchanged polls. If review does not start or an external blocker prevents progress, report the exact pending state instead of claiming completion.
2. Assess findings against the current diff. Fix valid issues within the authorized scope, verify the changed behavior, and push the fix. Bring disputed findings, scope expansion, or authorization decisions to the owner; do not blindly apply suggestions or dismiss them to clear a gate.
3. Once a finding is fixed, verified, and pushed, promptly resolve its review thread without waiting for renewed review. An outdated thread or successful CI alone does not prove that the finding is fixed. Re-read the thread list to confirm resolution and catch remaining discussions. Resolving a thread is neither review approval nor a guaranteed review trigger.
4. After resolving addressed threads, confirm that the configured review has started for the latest head and wait for current-head required checks and renewed review. Handle any new findings through the same cycle. Report completion only when required checks pass, review is complete, and no review threads remain unresolved; otherwise report the remaining blocker or owner decision. Include the PR link and verified head; merging remains the owner's responsibility.

This follow-through authorizes resolving addressed threads on the implementation PR. It does not authorize formal approvals, resolving disputed or unfixed findings, merging, or changing repository rules.

## Post-merge cleanup

**Owner confirmation 2026-10-05:** The owner grants standing authorization in `TaiwanCCyoyo/Stock` to update local `main` and delete the agent-created task branches and worktrees after confirming that the task PR has merged into `main`, without asking again. This includes the local task branch and its corresponding branch on the approved `origin`. It applies to the acting session's own task resources; unrelated or shared resources remain outside scope. Merging remains the owner's responsibility. The existing [submodule delivery authorization](#delivery-authorization) and [submodule handoff](stock-agent-operations.md#submodule-development-and-delivery) remain effective; cleanup does not add or revoke producer-development or delivery authority. Reset this repository-specific authorization when adopting the guidance elsewhere.

1. Verify the PR's merged state, destination repository, base `main`, final head, and merge commit from GitHub. Fetch `origin` and confirm that `origin/main` contains the merge commit; a closed PR alone is insufficient, and squash/rebase merges need not contain the original task commits.
2. Identify the exact task branch and worktree paths from Git's worktree inventory. Confirm that no other session uses them, their branch tips still match the merged PR's final head, and no uncommitted, untracked, or needed ignored files would be lost. Preserve needed files before removal; if ownership or preservation is uncertain, leave the affected resources intact and report the blocker.
3. Update local `main` in its existing checkout, or switch an available clean checkout to `main`, only when no other session is writing there. Run `git -c submodule.recurse=false pull --ff-only origin main` and verify local `main` matches the fetched `origin/main`. If local `main` has changes or diverges, stop cleanup and report; do not reset, stash unrelated work, or create a merge commit to force the update.
4. From a surviving checkout, remove only the verified task worktree and switch any surviving task checkout off the task branch before deleting it. Delete its local branch and the corresponding `origin` branch if it still exists; guard remote deletion with an explicit lease against the verified final head so newer commits cannot be removed. For squash/rebase merges, a forced local branch deletion is authorized only after the preservation checks above. Do not force worktree removal or delete unrelated branches, shared worktrees, or the primary checkout. Use the host's lifecycle tool for host-managed worktrees.
5. Report the updated `main` commit and removed or retained resources. If a resource cannot be safely cleaned up, preserve it and report why.

- Updating Stock `main` must not recursively update the primary producer checkout. Do not force removal when Git or the host lifecycle tool refuses a worktree with initialized submodules; preserve it and report the limitation rather than deleting its contents manually.
