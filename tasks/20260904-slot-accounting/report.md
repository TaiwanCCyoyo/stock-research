## 1. Bug 是什麼

V5 的 `on_bar` 用這一行決定還剩幾個槽：

```python
still_held = {code for code in data_dict if self.broker.get_position(code) > 0}
```

**`data_dict` 只包含當天有 K 棒的代碼。** 停牌／暫停交易中的持股不在裡面，所以**不佔槽位**，
書架會當作那個位子是空的再買一檔。每檔部位是 `初始資金 / top_k`，於是帳戶實際持有超過 `top_k`
檔——**未申報的槓桿，而且會隨書架變寬而放大**，正好就是 `20260904-book-size` 在量的那個軸。

修正是讀 broker 自己的部位帳（權威來源，包含今天沒報價的名字）：

```python
still_held = set(self.broker.positions)
```

**V5 沒有被改動。** 先前每一張卡的 stored run 都要能對它重現，改它會讓那些已提交報告的數字
悄悄變成另一個意思。修正放在新的 `rotation_ranker_v8.py`。

## 5. 這對先前的卡代表什麼，我不粉飾

**我這條線每一張用 V5／V4 的卡，都跑在一個會超額部署的引擎上。** retention 卡、ranking-horizon、
execution-delay、swap-rule 全部包含在內。

**相對結論大致仍成立**，因為每張卡的各臂跑在同一個缺陷上，缺陷對它們的影響方向相同——
13 條出場規則、9 格換股規則、延遲測試都是臂與臂的比較。**但「大致」是誠實的用字，不是保證**：
缺陷的大小隨換手率與槽數變化，所以換手率差異大的臂之間，比較被扭曲的程度不同。

**絕對數字全部要打折看待。** 我先前引用給你的「訓練期 88% 的交易日滿倉」「現金中位數 14.34M」
這類數字，來自受影響的 `slot_occupancy`（它另外還把賣出日多算一天，本卡的
`corrected_occupancy` 已修正）。

要不要重跑那幾張卡是成本問題，不是正確性問題——**我的建議是不重跑負面結果**（它們的結論是
「這條路沒用」，而缺陷不會把一條有用的路變成沒用），**但任何未來要當基準的正面結果，都必須
在 V8 上重跑**。
