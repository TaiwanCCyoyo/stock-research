# 任務卡：寬書架上的回吐停利 — 用「賣出規則」把週轉率買回來

`20260905-wide-giveback`，2026-09-05。**訓練期先跑，驗證期封存到第 4 節的訓練關卡全過為止。**
本文件在讀到任何 give-back 結果之前寫完。

## 1. 為什麼是這張卡

`20260904-book-size` 加上 `20260904-slot-accounting` 的修正，已經把 **K=30 的寬書架**確立成
目前唯一在驗證期站得住的槓桿：驗證期 K30 相對 K10 是 **120.4% vs 81.5% 報酬、−41.9% vs −53.3%
回落、capture 1.000 vs 0.722、pool share 0.1895 vs 0.0682**——四個指標同時贏。

**但 K=30 直接撞上擁有者講了很多次的那個限制。** 驗證期 K30 買了 **863 次**（訓練期 1515 次），
一個永遠塞滿三十檔的書架，既磨損成本、也不留任何「用手在合格名單裡挑」的空間。
`.tmp/notes-for-codex-20260905.md` 第 7 節把這件事寫成「這是偏好問題不是研究問題」——
**這張卡把它變回研究問題**：週轉率是**賣出規則**決定的，不是書架寬度決定的，而這兩件事到目前為止
一直被綁在一起測。

`20260826-runner-retention` 測過 give-back 家族，結論是負的——但那是**在 K=10 上**測的，
而 K=10 正是 retention/coverage 零和最緊的地方。`20260904-book-size` 的核心發現就是
**K=30 讓那個零和消失**（capture 到 1.000）。所以 give-back 在寬書架上值得重測一次，
**而且我預期它仍然會失敗**——見第 4 節的具名預測。

## 2. 手臂：不寫新程式

`tasks/20260904-slot-accounting/candidates/rotation_ranker_v8.py`，即已修正 slot 計算的那一支。
`exit_mode="giveback"` 是 V5 就有的模式，V8 繼承未改。**這張卡不新增任何 strategy 檔案**，
所以 `backtest_cli.py` 那個「`inspect.getmembers` 依字母序取第一個 `StrategyBase` 子類」的陷阱
（`20260904-execution-delay` 整個 grid 被它吃掉）在這裡沒有東西可以挑錯。

三個格子，只動一個軸：`top_k=30`、`exit_rank=30`、`min_hold_bars=20`、
分數 `r_ret_20 + r_ret_60` 全部固定，只有 `exit_param ∈ {0.20, 0.30, 0.40}`。

**基準是已存在的 `20260904-slot-accounting` K30 rank-exit 格子，兩個視窗都不重跑：**

| 訓練期 K30 rank（V8，已存） |          值 |
| --------------------------- | ----------: |
| 報酬                        |     148.74% |
| 最大回落                    |     −31.03% |

驗證期的 K30 rank 格子也已經存在，所以**訓練期若通過，只需要再開三個驗證期格子**，

## 3. 一個繼承下來、必須講清楚的不對稱

`rotation_ranker_v5` 的 docstring 寫明：`min_hold_bars` **只擋排名驅動的賣出**，
結構型停損（含 give-back）「fire whenever they fire」。**這是 give-back 手臂與 rank 基準之間
真實存在的不對稱**：基準的最短持有 20 根 K 是硬的，give-back 的不是。

在 K=10 上，這個不對稱本身就是 give-back 掉 capture 的一部分原因。它在 K=30 上依然存在。

**本卡的決定：原樣繼承、不修改。** 理由是這樣才和 `20260826-runner-retention` 的 give 手臂
可比——那是唯一一組已測過的對照。**代價是本卡無法把「賣出模式」和「有效持有長度」分開歸因**，
這一點寫在這裡，報告裡也必須再寫一次，不能事後才承認。

## 4. 關卡與預先宣告

### 4.1 主關卡：帳戶層級，不是每格層級

`20260826-runner-retention` 的 `weighted_turnover` 是**每個 slot** 的週轉率。擁有者的限制
（也是 codex `20260831` §7 gate 1 的定義）是**帳戶層級**的：年化資本週轉 ≤ 3.0 倍、
年化直接成本（手續費＋交易稅）≤ 2.0%。**這是兩個不同的量，本卡自己算帳戶層級的那一組**，
定義寫死在 `analyze.py`：

- `capital_turnover_per_year` = Σ(每筆買進金額 ÷ 該日帳戶淨值) ÷ 年數
- `cost_drag_per_year` = Σ((fee + tax) ÷ 該日帳戶淨值) ÷ 年數

兩個都用**買賣當日的帳戶淨值**，不是期初也不是平均，因為週轉率的意義是「相對當時的規模動了多少」。
基準格子用同一個函式重算，所以比較是同定義的。

### 4.2 六道訓練期關卡

| #   | 關卡                   | 門檻                                          |
| --- | ---------------------- | --------------------------------------------- |
| 1   | 帳戶年化資本週轉       | **≤ 3.0**                                     |
| 2   | 帳戶年化成本磨損       | **≤ 2.0%**                                    |
| 3   | pool share（1.5 門檻） | **≥ 0.80 × 0.25679 = 0.20543**                |
| 4   | capture rate           | **≥ 0.60**                                    |
| 5   | 最大回落               | 不比基準的 −31.03% 差超過 **5.0pp**           |
| 6   | 平台                   | give20 / give30 / give40 **三格連續**全過 1–5 |

關卡 6 是 `20260826-tail-selection` 之後每張卡都用的規則：**一個有序參數家族只有一格過，
是抽樣噪音的形狀，不是效應的形狀。** `20260904-swap-rule` 十三格只有一格全過、沒有平台，
就是照這條判負的。

### 4.3 具名的、有號的預測（寫在看到結果之前）

`20260826-runner-retention` 在 **K=10** 上量到：give30 capture **0.47**、give40 **0.33**，
對照 rank 的 0.94；pool share 0.123 → 0.113 / 0.083。

**我預測 K=30 的 give30 會落在 capture ≥ 0.60 且 pool ≥ 0.2054。**
理由是寬書架把 coverage 的零和解掉了（K30 rank 的 capture 是 1.000，K10 只有 0.906），
所以同一個賣出規則在 K30 應該吐掉比較少。

**codex 的 `give30__k30__initial` 在她自己的管線上讀到 capture 0.635 / pool 0.2380。**
那是一個獨立寫成的先驗，正好落在我的預測區間內。**如果我的數字離她的很遠，那不是噪音，
那是 `20260904-slot-accounting` 已經隔離出來的「飆股母體定義差異」的量測**——引擎已經對到小數點，
剩下的差就在那裡。這個比對本身是這張卡的副產品，而且是免費的。

### 4.4 預先指定的三種結論

| 訓練期結果                                    | 結論                                                 | 下一步                                    |
| --------------------------------------------- | ---------------------------------------------------- | ----------------------------------------- |
| 三格全過 1–5                                  | **正面**：寬書架上可以用賣出規則把週轉率換回來       | 開驗證期三格                              |
| 有格子過但無平台，或 give30 的 capture < 0.60 | **負面**：K=30 沒有解掉 give-back 的 coverage 代價   | 不開驗證期，寫進 `trading-objective` 記憶 |
| pool 過但週轉率 > 3.0                         | **無效**：這張卡的前提（賣出規則決定週轉率）本身錯了 | 不開驗證期，改測部位大小                  |

第三種結論值得特別講：如果 give-back 在 K=30 上**沒有**大幅降低週轉率，那代表週轉是
**排名淘汰**造成的而不是停利造成的，這張卡問錯了問題，而那個資訊本身有用。

## 5. 驗證期政策

**訓練期關卡全過之前不讀驗證期。** 這是我這條線從 `20260903-entry-window` 開始才做到的事
（在那之前十張卡有十張開了驗證期），也是 codex 那條線一開始就在做的事。
通過的話只開三格，並且**在開之前把 4.4 的表當成已簽字的合約**——`20260904-book-size` 就是
這樣跑的，那是我目前唯一一個站得住的正面結果。

## 6. 修訂（2026-09-05，寫在跑 give25 / give35 之前）

**訓練期第一輪的結果：`give30` 五道關卡全過，`give20` 與 `give40` 都沒過，所以第 4.2 節的
關卡 6（平台）失敗，第 4.4 節指定的結論是「負面」。**

本節不推翻那個結論，而是**測試它失敗的其中一個具名原因**：0.20 / 0.30 / 0.40 的間距是
10 個百分點，如果真正的最佳點有寬度但寬度小於 10pp，這個網格看不到平台，看到的會是尖峰。
兩種情況在既有的三格上長得一模一樣。

**加測 `give25` 與 `give35`，並且預先宣告：**

- **兩格都通過第 4.2 節的關卡 1–5** → 平台存在於較細的解析度上，家族是真的，改開驗證期。
- **任一格沒過** → **第一輪的負面結論成立且最終**，不開驗證期，寫進記憶。

這是對「為什麼沒有平台」的一個可證偽的替代解釋做檢定，不是把門檻搬到結果後面。
關卡 1–5 的數值一個字都不動，`analyze.py` 也不動。**如果失敗，這張卡就是負面的。**
